*这是对讲座简介的[Why WebGPU](../introduction.md#why-webgpu)]部分的更详细解释。*

当我在计算机图形课程中寻找**最佳的图形 API 来教授**时，我对使用 WebGPU 进行本机开发的兴趣与日俱增。

```{important}
图形 API 在过去 20 年中发展得非常快（想想 OpenGL 1.1 对于那些了解它的人来说是什么样子），因此重要的是讲座要以合理的速度跟随这种发展。
```

很长一段时间以来，我一直在教授**OpenGL**。这是一个用于与 GPU 交互的完美标准和跨平台 API。但多年来，这个 API 及其习惯用法开始成为**遗产**。
首先，Apple 在 4.1 版本之后停止支持它（让我感到沮丧，因为无法在讲座中使用 [DSA](https://www.khronos.org/opengl/wiki/Direct_State_Access) 等），并从 macOS 10.14 开始（自 2018 年起）一起**弃用**它。基本上，他们可以随时放弃它，所以现在教授 OpenGL 确实**不是一个面向未来的赌注**。

其次，很明显无论如何都不会出现新版本的 OpenGL。其指导联盟目前正在研究 **Vulkan**。尽管采用了全新的设计，Vulkan 仍然是一个跨平台的 API，甚至统一了桌面和移动平台，因此从长远来看能够完全取代 OpenGL。 **但是**...苹果又来了。

与图形世界的许多参与者一样，**Apple** 在 2010 年代初期感到需要从 OpenGL 的设计中发展（OpenGL 与硬件的发展方式相差太大），并启动了自己的 API，称为 **Metal**。但与其他人不同的是，他们**拒绝加入** Vulkan 计划。因此，尽管有[在 Apple 设备上使用 Vulkan 的方法](https://www.lunarg.com/wp-content/uploads/2021/06/The-State-of-Vulkan-on-Apple-03June-2021.pdf)，但我们还不能真正认为 Vulkan 足够跨平台。我不希望我的讲座让 macOS 用户感觉有点被黑客攻击。

对于所有试图同时支持 Linux、Windows 和 macOS（更不用说移动平台）的软件供应商来说，图形 API 的这种分散状态是一个**令人担忧的问题**。他们被迫在不同的 API 中实现相同的流程，在分解这些并行实现的同时，他们中的许多人自发地最终编写了**自定义图形抽象**库。

**我们应该教授这样一个抽象库吗？** 我很不愿意这样做。他们中的许多人做出了与其开发环境相关的特定领域的选择。它们往往是不完整的，因为没有足够的时间来使它们可重用。这些库的寿命可能比更标准化的 API 之一（它们本身已经消亡得太快了）要短得多。它们可能会强制执行不常见的特定习惯用法，从而使向其他图形 API 的过渡变得更加困难。

**Web 联盟**在尝试向 JavaScript 代码公开统一的 GPU 抽象时面临着同样的问题，他们起草了 [WebGPU](https://gpuweb.github.io/gpuweb).

该 API 拥有不断增长的开发人员/文档基础，具有通用性、跨平台性和面向未来的特点，因此使其成为桌面应用程序的良好候选者！这就是为什么 Google Chrome 对此 API 的实现被设计为一个单独的代码库，称为 [Dawn](https://dawn.googlesource.com/dawn)，并且可以由其他应用程序链接。
